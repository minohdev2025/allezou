## 0. Avant de valider — mes désaccords et décisions

Tu m'as demandé de te dire où je ne suis pas d'accord **avant**. Les voici, classés par sévérité.

### D1 — `[À DÉCIDER]` Réutilisation de briques LiNX → **je recommande : non, et je suis plus tranché que ta recommandation**

Tu proposes « indépendant, car les modèles de tenancy sont différents ». Je pousse plus loin : je recommande **zéro partage de code avec LiNX au démarrage**, y compris les helpers DB génériques.

- Ton `lib/db/visibility.ts` est une porte d'accès unique, testée, à du SQL non trivial. La copier depuis LiNX amènerait avec elle un héritage (conventions de nommage, gestion d'erreurs, format de log) qui n'a pas lieu d'être ici.
- L'auth LiNX est probablement calée sur un modèle métier (employés d'un bureau d'architecture) qui n'a rien à voir avec un parent qui clique un lien WhatsApp.
- Le couplage via un monorepo « shared » pour deux projets de tailles très différentes est presque toujours une perte nette en phase de construction : on passe son temps à faire respecter des abstractions à un seul consommateur.

**Si** tu as des helpers **vraiment** génériques (parsing d'erreurs Postgres, formatage de dates, génération d'UUID v7, calcul de hash), ils peuvent vivre dans un package npm privé **après** que les deux projets aient stabilisé leur propre usage. Pas avant.

**Décision que je prends en l'absence d'instruction** : dépôt totalement indépendant, `package.json` propre, aucune dépendance symbolique vers LiNX.

### D2 — `kind` sur `outing` est trop grossier — proposition de nuance

`outing_kind` n'a que deux valeurs (`spontaneous`, `planned`) et la contrainte `spontaneous_has_expiry` rend la présence au parc et l'inscription au musée du même week-end symétriques. C'est élégant, mais je vois deux risques opérationnels :

1. **Notifications très différentes.** Une présence au parc est utile maintenant ; une inscription à un atelier samedi prochain est utile la veille, pas maintenant. Les pousser avec la même mécanique et un plafond journalier commun risque de priver la première au profit de la seconde.
2. **Filtrage d'écran différent.** « Maintenant » ne devrait jamais afficher une `planned` non commencée. « Agenda » ne devrait jamais afficher une `spontaneous` expirée. Le tri reposera donc sur une combinaison de `kind` + `now()` + `starts_at` + `expires_at`, ce qui complique chaque requête.

**Mon choix** : je garde `outing_kind` à deux valeurs pour la V1, mais je **sépare les flux de notification** : la limite des 4/jour s'applique séparément aux spontanées et aux planned (4 + 4). Justification : les deux signaux ne se cannibalisent pas.

**Si tu n'es pas d'accord**, dis-le maintenant — c'est trivial à changer en V1, coûteux en V2.

### D3 — Le `description` text libre sur `outing` est un nid à dérive

Tu autorises `description text` sur `outing`, et la section 11 borne les champs libres mais ne fixe pas de longueur. Une description longue change la nature du produit : on passe d'un statut (« je suis là ») à un mini-événement décrit. Et la modération de l'ingestion (LLM) est imprécise sur les descriptions longues — on se retrouve à afficher des blobs.

**Mon choix** : `description` limitée à **280 caractères**, validée par Zod. C'est la borne Twitter classique, elle suffit pour « ramène ton maillot, pataugeoire intérieure » et rien de plus. La V2 pourra l'ouvrir.

### D4 — L'ingestion par LLM est un risque produit et budget que le prompt sous-estime

Section 8 : « `html_llm` » est listé au même titre que `jsonld` et `ical`, comme un adaptateur de troisième rang. C'est honnête sur le plan technique mais trompeur sur le plan opérationnel :

- Un LLM pour 6–8 sources genevoises, c'est un coût direct, une latence (3–8 s par page), et surtout **un risque qualité** : tu auras des hallucinations de date et de prix. La modération humaine absorbe une partie, mais si le dimanche soir le parent voit trois événements faux, il ne revient pas.
- La plupart des agendas communaux suisses exposent **soit** un flux iCal/JSON-LD, **soit** rien d'exploitable — auquel cas il vaut mieux appeler la commune et demander le flux que de scrapper leur page.

**Mon choix** : V1 = `jsonld` + `ical` exclusivement, sur des sources confirmées. `html_llm` existe en base (schéma) mais **n'est jamais instancié en Phase 5**. On l'activera en V2 quand on aura un panel d'agendas validés et qu'on saura si l'effort en vaut le coût. Justification : P5 (minimisation) et P8 (pas de surprise côté qualité).

### D5 — Pas de canal explicite pour la suppression de compte en `family`

Section 11 : « suppression de compte effective ». Mais `family.deleted_at` est un soft delete et il n'y a pas de vue agrégée qui dit « quand on supprime un foyer, voici ce qui disparaît ». Le `ON DELETE CASCADE` des FK fait le travail physique, mais :

- `circle.created_by` est un FK, donc la suppression du créateur d'un cercle casse le cercle. Mauvais.
- Les `outing.created_by` et `source.created_by` (et `place.created_by`) ont le même problème en cascade.

**Mon choix en l'absence d'arbitrage** : à la suppression d'un `family`, je transforme les `*_by` sortants en `NULL` (pas de cascade) et je conserve `circle` orphelin. Si un cercle n'a plus aucun admin actif, il est marqué `archived_at`. Le `child` cascade, le `participation` cascade, le `circle_membership` sort par `left_at` posé à `now()`.

Je note que `circle_invite.created_by` et `audit_log.family_id` ont déjà des comportements différents (`audit_log` est `ON DELETE SET NULL`, `invite` cascade) — il faut aligner.

### D6 — `audit_log` ne devrait pas être un texte libre

`action text NOT NULL` est ouvert à tout. Ça marchera, mais le jour où on veut corréler (« combien de révocations d'invitation ce mois ? ») on sera bloqué. À l'inverse, une enum ferme nous interdit d'ajouter une action sans migration.

**Mon choix** : `action` reste `text`, mais avec un **whitelist** côté code, validée par Zod, et documentée dans `docs/DECISIONS.md`. Pas d'enum SQL. Compromis raisonnable.

### D7 — `place.is_verified` sans workflow

`is_verified boolean` existe, mais personne ne sait qui vérifie, comment, et à quelle fréquence. Pour le pilote (3 classes), ça reste gérable à la main. Mais ça veut dire que dans `visibility.ts`, les lieux non vérifiés sont-ils filtrables ? accessibles ? Je pose la question et je propose : **affichés tels quels, marqués visuellement d'un indicateur discret**, sans filtrage. C'est cohérent avec P5 (on ne complique pas le modèle) mais ça veut dire qu'un lieu ajouté par un parent rentre dans le catalogue de tous les cercles. Tu valides ?

### D8 — `muted_until` plutôt qu'un vrai mode « silence »

`muted_until timestamptz` sur `circle_membership` est minimal. Mais P4 parle d'un bouton « ne rien recevoir pendant 7 jours ». 7 jours, ce n'est pas un timestamp — c'est une intention.

**Mon choix** : `muted_until` reste le mécanisme, et un bouton « 7 jours » pose `muted_until = now() + interval '7 days'`. C'est plus simple qu'un champ `mute_mode enum('forever','until','hours')` qui n'apporte rien.

### D9 — `circle_invite.max_uses` à `smallint` me gêne

`smallint` = 32 767. Pour une invitation de classe, ça suffit. Mais un référent qui partage son lien dans 5 groupes WhatsApp et oublie de couper pourrait largement dépasser ce chiffre, et le `use_count` partirait en erreur. Petit, mais cheap à corriger.

**Mon choix** : `smallint` → `integer`. Trivial.

### D10 — Identité du responsable de traitement

Section 12 : `[À DÉCIDER]`. Je ne tranche pas — c'est juridique. Mais je note que **la page « Vos données » ne peut pas être écrite avant que ce point soit arbitré**. Je la marque comme blocage explicite en Phase 6, pas comme un oubli.

## 1. Architecture cible (résumé)

Une PWA Next.js 15 App Router, TypeScript strict, PostgreSQL 16, SQL brut via un pool `pg`, serveur de mail sortant minimal (SMTP Infomaniak), hébergement Infomaniak, Docker Compose. Pas d'ORM, pas de service tiers recevant des données.

Trois invariants traversent tout le code :

1. **Visibilité unique.** Toute lecture sociale passe par `lib/db/visibility.ts`. Aucun autre fichier ne touche `participation`, `participation_share`, `outing` ou `circle` en SQL.
2. **Validation à la frontière.** Tout input client (formulaire, Server Action, route handler) passe par un schéma Zod avant tout accès base.
3. **État de vérité calculé.** Les expirations et l'appartenance active sont lues avec `now()` à chaque requête. Pas de cache applicatif sur ces champs en V1.

### Dépendances justifiées (uniquement ce qui sort du standard)

Je n'introduis rien sans le déclarer. Verrouillage en Phase 1 :

| Package | Rôle | Pourquoi pas le stdlib / l'existant |
|---|---|---|
| `next@15` | Framework | Imposé par le brief |
| `react@19`, `react-dom@19` | UI | Imposé |
| `typescript@5` | Types | Imposé |
| `pg` | Driver Postgres | Imposé (SQL brut) |
| `zod` | Validation schémas | Le brief le mentionne ; pas de validation type-safe équivalente en stdlib JS |
| `jose` | JWT, signature magic link | Standard de fait ; `crypto` stdlib n'a pas de wrapper ergonomique |
| `web-push` | Web Push VAPID | Imposé par PWA ; `crypto` ne fait pas l'encapsulation |
| `ical.js` | Parser iCal | Aucun équivalent en stdlib ; patch sur mesure = dette |
| `jsonld` | Parser JSON-LD | Idem |
| `vitest` | Test runner | Standard de fait pour Vite/Next ; Jest plus lourd, plus lent |
| `@testing-library/*` | Tests composants | Standard |
| `playwright` | E2E | Standard, requis pour test bout-en-bout critique |
| `pino` | Logger structuré | `console.*` pollue la prod ; format JSON aide aux requêtes |

**Tout le reste est à justifier le moment venu.** Pas de `date-fns` (on utilise `Intl` et un module interne `time.ts`), pas de `lodash`, pas de `clsx` (template literals suffisent), pas de Tailwind (CSS modules + tokens, plus simple à auditer), pas de shadcn (overhead d'abstractions pour une UI à 3 écrans).

## 3. Schéma SQL — migration unique `0001_init.sql`

Cette migration est livrée complète. Elle reprend la section 4 du brief et applique les décisions D3 (description 280), D5 (FK sortantes en `ON DELETE SET NULL`), D6 (action texte), D7 (lieux non vérifiés OK), D9 (`integer` pour `max_uses`).

```sql
-- 0001_init.sql
-- Totir — schéma initial
-- Pré-requis : PostgreSQL 16, extension citext

BEGIN;

CREATE EXTENSION IF NOT EXISTS citext;

-- ─────────────────────────────────────────────────────────────────
-- 0. Conventions
-- ─────────────────────────────────────────────────────────────────
-- UUID v7 partout. Pas de SERIAL exposé.
-- Tous les horodatages : timestamptz. Fuseau applicatif : Europe/Zurich.
-- FK sortantes vers family : ON DELETE SET NULL (préserve la cible).
-- FK sortantes vers participation/circle : CASCADE (la cible dépend de la source).
-- ON DELETE CASCADE interne à un cercle (child → family, membership → family) : OK.

-- ─────────────────────────────────────────────────────────────────
-- 1. Foyers et enfants
-- ─────────────────────────────────────────────────────────────────
CREATE TABLE family (
  id            uuid PRIMARY KEY,
  display_name  text NOT NULL,
  email         citext UNIQUE,                   -- lien de connexion uniquement
  locale        text NOT NULL DEFAULT 'fr-CH',
  created_at    timestamptz NOT NULL DEFAULT now(),
  last_seen_at  timestamptz,
  deleted_at    timestamptz
);

CREATE TABLE child (
  id          uuid PRIMARY KEY,
  family_id   uuid NOT NULL REFERENCES family(id) ON DELETE CASCADE,
  first_name  text NOT NULL,
  birth_year  smallint NOT NULL CHECK (birth_year BETWEEN 2005 AND 2035),
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX child_family_idx ON child (family_id);

-- ─────────────────────────────────────────────────────────────────
-- 2. Cercles
-- ─────────────────────────────────────────────────────────────────
CREATE TYPE circle_kind AS ENUM ('class', 'school', 'neighborhood', 'custom');
CREATE TYPE member_role AS ENUM ('admin', 'member');

CREATE TABLE circle (
  id           uuid PRIMARY KEY,
  name         text NOT NULL,
  kind         circle_kind NOT NULL DEFAULT 'custom',
  created_by   uuid REFERENCES family(id) ON DELETE SET NULL,  -- D5
  created_at   timestamptz NOT NULL DEFAULT now(),
  archived_at  timestamptz
);

CREATE TABLE circle_membership (
  circle_id           uuid NOT NULL REFERENCES circle(id) ON DELETE CASCADE,
  family_id           uuid NOT NULL REFERENCES family(id) ON DELETE CASCADE,
  role                member_role NOT NULL DEFAULT 'member',
  joined_at           timestamptz NOT NULL DEFAULT now(),
  left_at             timestamptz,
  notify_spontaneous  boolean NOT NULL DEFAULT true,
  notify_planned      boolean NOT NULL DEFAULT true,
  muted_until         timestamptz,
  PRIMARY KEY (circle_id, family_id)
);

CREATE INDEX membership_active_idx
  ON circle_membership (family_id)
  WHERE left_at IS NULL;

CREATE TABLE circle_invite (
  id          uuid PRIMARY KEY,
  circle_id   uuid NOT NULL REFERENCES circle(id) ON DELETE CASCADE,
  code_hash   text NOT NULL,
  created_by  uuid NOT NULL REFERENCES family(id),
  expires_at  timestamptz NOT NULL,
  max_uses    integer,                                 -- D9
  use_count   integer NOT NULL DEFAULT 0,              -- D9
  revoked_at  timestamptz
);

CREATE INDEX invite_circle_active_idx
  ON circle_invite (circle_id)
  WHERE revoked_at IS NULL AND expires_at > now();

-- ─────────────────────────────────────────────────────────────────
-- 3. Lieux
-- ─────────────────────────────────────────────────────────────────
CREATE TABLE place (
  id           uuid PRIMARY KEY,
  name         text NOT NULL,
  address      text,
  commune      text,
  lat          numeric(9,6),
  lng          numeric(9,6),
  is_indoor    boolean,
  is_verified  boolean NOT NULL DEFAULT false,
  osm_id       text UNIQUE,
  created_by   uuid REFERENCES family(id) ON DELETE SET NULL,  -- D5
  created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX place_commune_idx ON place (commune) WHERE commune IS NOT NULL;

CREATE TABLE circle_place (
  circle_id   uuid NOT NULL REFERENCES circle(id) ON DELETE CASCADE,
  place_id    uuid NOT NULL REFERENCES place(id) ON DELETE CASCADE,
  sort_order  smallint NOT NULL DEFAULT 0,
  PRIMARY KEY (circle_id, place_id)
);

-- ─────────────────────────────────────────────────────────────────
-- 4. Sorties et participations
-- ─────────────────────────────────────────────────────────────────
CREATE TYPE outing_kind   AS ENUM ('spontaneous', 'planned');
CREATE TYPE outing_source AS ENUM ('parent', 'scraped', 'partner');

CREATE TABLE outing (
  id            uuid PRIMARY KEY,
  kind          outing_kind NOT NULL,
  source        outing_source NOT NULL,
  is_public     boolean NOT NULL,
  title         text,
  description   text CHECK (description IS NULL OR length(description) <= 280),  -- D3
  place_id      uuid REFERENCES place(id) ON DELETE SET NULL,                    -- D5
  starts_at     timestamptz NOT NULL,
  ends_at       timestamptz,
  expires_at    timestamptz,
  age_min       smallint,
  age_max       smallint,
  price_chf     numeric(7,2),
  booking_url   text CHECK (booking_url IS NULL OR length(booking_url) <= 2048),
  is_indoor     boolean,
  created_by    uuid REFERENCES family(id) ON DELETE SET NULL,                    -- D5
  offer_id      uuid,                  -- extension partenariats, inutilisé V1
  cancelled_at  timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT public_implies_no_creator
```
